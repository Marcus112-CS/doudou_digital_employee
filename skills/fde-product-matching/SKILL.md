# 需求与产品匹配

输入为客户原话、业务目标、已购或正在使用的服务，以及可用产品目录。会前公开背景仅作为待核实线索。

## 判断与检索

1. 区分明确需求、当前故障、能力咨询和潜在机会。优先确认现有服务是否已经覆盖；故障或投诉阶段先支持问题解决。
2. 将需求拆成具体能力，提炼短关键词，例如“车辆识别”“事件派单”“状态展示”。每次 search_products 传 1–12 个关键词，避免整段客户材料作为关键词。
3. 工具已挂载时调用 search_products，再用 get_product 核对候选详情；未挂载时检索有来源的内部资料。未命中时可以按业务同义词再查一次；仍无结果则说明当前目录缺口。不能推断公司一定没有该能力。
4. 逐项核对 capabilities、prerequisites、exclusions 和来源时效。关键词命中数量不是适配概率。资料过期、未设置有效期或事实冲突时明确列为待核实。
5. 结果 demo=true 时在输出开头写“以下为演示匹配，不代表公司真实产品”。没有真实目录时可以展示流程，不能生成真实报价、案例和效果承诺。
6. 给出“有条件适配 / 信息不足 / 当前不适配 / 现有服务已覆盖”的判断和依据。产品负责人或协同入口可通过 lookup_collaboration 查询，负责人未核实时不编造联系人。

## 输出

客户需求及其确认状态，然后给出候选表：

| 能力需求 | 候选产品及 ID | 匹配依据 | 前提与不支持项 | 待确认问题 | 建议下一步 |
|---|---|---|---|---|---|

按本次沟通需要补一段客户介绍：先回应客户问题，再提出澄清或讨论能力的邀请。对外素材可用 get_product 的 audience=external 视图；内部备注和归属信息留在内部建议。该参数只裁剪目录字段，FDE 仍需确认最终稿是否适合对外。

## 例子

客户说“每次都要人工判断是否扩容”。应先问现有监控和容量判断流程，再核实当前服务是否包含容量分析；没有适用产品时记录缺口。不能仅凭“扩容”关键词推荐销售，更不能自行承诺节省比例。

“事件处置工单”与“车辆事件分析”可能组合，但前者不因此具备车辆识别能力。每项能力分别引用对应产品说明。
